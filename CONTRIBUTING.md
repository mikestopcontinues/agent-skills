# Contributing

The toolkit ships from one TypeScript authoring surface
(`generator/canonical-sources/`) into per-harness bundles (`claude/`,
`codex/`, `opencode/`). All edits start in canonical sources; bundles are
regenerated by `pnpm run build`.

## Setup

```bash
git clone git@github.com:mikestopcontinues/agent-skills.git
cd agent-skills
pnpm install
pnpm run check               # type + lint + test + bundle drift — must pass green
```

Node ≥ 24 (native TypeScript type-stripping; `.ts` runs without compile).
pnpm 10. No build step before running tests.

Other scripts:

| Command | What it does |
|---------|--------------|
| `pnpm run build` | One-shot rebuild of `claude/`, `codex/`, `opencode/`, both `marketplace.json` files |
| `pnpm run dev` | Watch mode — auto-rebuilds on changes under `generator/{canonical-sources,emit,factories,aliases}/` (uses Node 24's `--watch-path`; no dep) |
| `pnpm run test:watch` | Vitest in watch mode |
| `pnpm run type:watch` | `tsc --noEmit --watch` |
| `pnpm run check:bundles` | Build + `git diff --quiet` on bundle dirs — fails if bundles drifted from canonical sources |

## How a canonical source is shaped

Each artifact is two or three files in the same canonical-sources directory,
sharing a base name:

| Kind | Files |
|------|-------|
| Skill | `<name>.ts` (defineSkill call) + `<name>.md` (body) + optional `<name>.extras/` (per-skill shipped files like focus briefs) |
| Agent | `<name>.ts` (defineAgent call) + `<name>.md` (system prompt) |
| Hook | `<name>.ts` (defineHook call) + `<name>.sh` (bash handler) + optional `<name>.test/` (JSON fixtures the harness runs against the script) |
| Script | A single executable file under `generator/canonical-sources/scripts/` |

The `define*` factories validate against Valibot schemas at module load —
malformed sources fail fast with a typed error pointing at the bad field.
TypeScript catches the same shape errors at compile time via `alignSchema`.

## Add a skill (end-to-end)

```bash
# 1. Create the three files
cat > generator/canonical-sources/skills/my-skill.ts <<'EOF'
import { defineSkill } from '../../factories/defineSkill.ts';
import { loadText } from '../../factories/loadText.ts';

export const skill = defineSkill({
  name: 'my-skill',
  description: 'One-sentence prescriptive description — when to invoke this skill.',
  body: loadText(import.meta.url, 'my-skill.md'),
});
EOF

cat > generator/canonical-sources/skills/my-skill.md <<'EOF'
The full SKILL.md body — instructions for the agent invoking this skill.
EOF

# 2. (Optional) ship extras alongside the skill
mkdir -p generator/canonical-sources/skills/my-skill.extras/focuses
cat > generator/canonical-sources/skills/my-skill.extras/focuses/accuracy.md <<'EOF'
# Accuracy focus brief
EOF

# 3. Regenerate bundles + verify everything is consistent
pnpm run build
pnpm run check

# 4. Commit canonical sources AND the regenerated bundles together
git add generator/canonical-sources/skills/my-skill.* claude/skills/my-skill codex/skills/my-skill opencode/skills/my-skill
git commit -m "feat(skills): add my-skill — <one-liner why>"
```

The marketplace `skills[]` arrays in `.claude-plugin/marketplace.json` and
`.agents/plugins/marketplace.json` regenerate automatically — no manual list
update.

## Add an agent

```ts
// generator/canonical-sources/agents/my-persona.ts
import { defineAgent } from '../../factories/defineAgent.ts';
import { loadText } from '../../factories/loadText.ts';

export const agent = defineAgent({
  name: 'my-persona',
  description: 'One-sentence cognitive lens — what this agent is good at.',
  model: 'opus',                                   // or 'sonnet' | 'haiku'
  tools: ['Read', 'Grep', 'Glob', 'Write', 'Bash'], // canonical tool names
  prompt: loadText(import.meta.url, 'my-persona.md'),
});
```

Tool names are canonical (`Read`, `Write`, `Edit`, `Bash`, `Glob`, `Grep`,
`Dispatch`, etc.); the emitter translates `Dispatch` to each harness's
subagent-dispatch tool (`Dispatch` for CC, `spawn` for Codex, `task` for
OpenCode) via `generator/aliases/toolNames.ts`. Add a canonical tool name
in `generator/factories/types/toolNames.ts` if you need one that isn't
listed.

## Add a hook

```ts
// generator/canonical-sources/hooks/my-hook.ts
import { defineHook } from '../../factories/defineHook.ts';
import { loadText } from '../../factories/loadText.ts';

export const hook = defineHook({
  name: 'my-hook',
  event: 'PreToolUse',          // PreToolUse | PostToolUse | SessionStart | …
  matcher: 'Bash',              // tool name or pipe-alternated (e.g. 'Edit|Write')
  handler: { kind: 'bash', command: loadText(import.meta.url, 'my-hook.sh') },
});
```

The handler script reads the harness's hook input JSON from stdin (e.g.,
`{ "tool_input": { "command": "git status" } }` for `PreToolUse`/`Bash`),
performs its check, and either exits 0 (allow) or writes a CC-style
`hookSpecificOutput` JSON to stdout with `"permissionDecision": "deny"` and
a `"permissionDecisionReason"` (the harness surfaces the reason to the
caller). See any existing hook in `generator/canonical-sources/hooks/` for
the pattern.

If you ship test fixtures alongside the hook (recommended), drop them as JSON
files under `<name>.test/` plus a sibling `expected.json` declaring the
outcome per fixture:

```
generator/canonical-sources/hooks/my-hook.test/
  allow-normal-case.json
  deny-edge-case.json
  passthrough-no-match.json
  expected.json                 ← declares what each fixture should do
```

Each fixture file is a real hook input (what stdin sees) with paths using
`__PROJECT_ROOT__` as a placeholder for `$CLAUDE_PROJECT_DIR`:

```json
{
  "tool_name": "Write",
  "tool_input": { "file_path": "__PROJECT_ROOT__/docs/notes/foo.md" }
}
```

`expected.json` maps fixture-name → expected outcome:

```json
{
  "allow-normal-case": { "deny": false },
  "deny-edge-case":    { "deny": true, "reasonContains": "Cannot write" },
  "passthrough-no-match": { "deny": false, "createFiles": ["docs/notes/foo.md"] }
}
```

The runner ([tests/hook-fixtures.test.ts](tests/hook-fixtures.test.ts)) creates
a fresh tmp dir per fixture, optionally pre-creates files (`createFiles`) or
directories (`createDirs`) the hook needs, substitutes `__PROJECT_ROOT__`,
pipes the JSON to the hook script, and asserts the deny outcome.

To activate testing for a new hook, add its name to the `COVERED_HOOKS` array
in the runner. The runner asserts that `expected.json` covers every fixture
in the directory (no orphans, no extras) — so adding a fixture without
declaring its outcome fails loudly.

**Limitation**: this runner currently only handles hooks whose behavior is
filesystem-pattern-based, not git-state-based. Hooks like `block-main-edits`
and `pre-commit-gate` need a per-fixture `git init` setup that isn't wired
yet — their fixtures sit in their `.test/` directories without an
`expected.json` for now. Extending the runner to handle git-state hooks is
welcome.

## Add a project-context template

Skills like `start-session` consume project context (the captain's
project-level notes). Add or modify a template under
`generator/canonical-sources/contexts/`. The emitter ships it to each
harness's project-context location.

## Code conventions

- **camelCase keys throughout canonical sources.** Frontmatter dialects
  (kebab-case for CC, varied for Codex) are an emit-time concern; the
  emitter transforms.
- **Sidecar files for human content.** Skill bodies, agent prompts, hook
  scripts — anything you'd want to edit in a text editor with markdown /
  bash highlighting — lives in a sidecar, not a string literal in the
  `.ts` file.
- **Comments only when the WHY isn't obvious from the code.** No
  comments restating function names. No comments describing the current
  task or commit context.
- **`erasableSyntaxOnly` TypeScript.** No enums, no `namespace`, no
  parameter properties — the canonical sources run unmodified under Node.
- **One artifact per file**, with `export const skill | agent | hook | context`.
  The loader globs the directory; no import list to maintain.
- **Bodies are not lifted from prior locations** — they're authored here.
  Don't reference removed `.claude/` paths in body prose.
- **No emojis** unless the captain explicitly asks for them.

## Before you commit

```bash
pnpm run check    # type + lint + test + bundle-drift (must pass green)
```

The `check:bundles` step runs `pnpm build` then `git diff --quiet` on the
bundle directories — so if you edited canonical sources without rebuilding,
this gate catches it.

For your local dev loop against a live harness (CC / Codex / OpenCode), see
the "Local development against a live harness" section of [README.md](README.md).

## Commit discipline

- **Many small commits**, each leaving the repo green.
- **`pnpm run check` passes before every commit** — bundles are committed
  alongside the canonical-source change that produced them.
- **Commit messages explain "why".** What the change does is in the diff;
  why it was made isn't.
- **Conventional commit prefixes**: `feat(<scope>):`, `fix(<scope>):`,
  `docs(<scope>):`, `refactor(<scope>):`, `test(<scope>):`,
  `chore(<scope>):`. Scope is usually a harness (`codex`, `claude`,
  `opencode`), a layer (`generator`, `canonical-sources`), or an artifact
  (`skills`, `agents`, `hooks`).

## Versioning policy (pre-1.0)

`package.json#version` is the source of truth — each per-harness `plugin.json`
inherits it via `emit*FromPackage`. Pre-1.0, the policy is: **bump
`0.1.PATCH` on every commit that changes plugin-loaded content** (canonical
sources, bundles, hooks/agents). Doc-only or generator-only commits don't
need a bump.

Why the discipline matters: `claude plugin update agent-skills@agent-skills-dev`
is a no-op when the version field is unchanged. Without a bump, every dev
loop requires the heavier `claude plugin uninstall && claude plugin install`
to refresh CC's plugin cache (Codex's `marketplace upgrade` always refreshes
regardless of version; OpenCode `npm link` is symlinked so it doesn't cache).

`pnpm run release` is the helper:

```bash
# Bumps 0.1.N → 0.1.(N+1), regenerates bundles, stages package.json + bundles.
# You commit the result.
pnpm run release patch     # 0.1.0 → 0.1.1
pnpm run release minor     # 0.1.0 → 0.2.0  (use for breaking namespace / API changes)
```

For the first public 1.0 release, this section will gain a CHANGELOG +
release-checklist sub-section.
